# 架构地图（从代码画）

用户的痛点：项目迭代太快，自己把握不住全貌。产物是一套**地图**：从总览一层层点进去就能看懂项目，
每条线都有**证据**——读代码确认过、标了出处，不是看名字猜的。一张画错的图比没有图更糟。

**先读 [`FORMAT.md`](FORMAT.md)**：结构、写法、`@src` 锚点、`@note`、`changed` / `planned` 标记、校验都在那里。
本机工具：`mmd`（静态出图）、`mmd-view`（交互看图）、`scripts/check.py`（校验）。

**省 token 是硬要求**：已有的地图就是这个项目的索引。更新时以它为准，只读改动的部分，
不重新勘察没变的模块；能看 diff 就不读整个文件，能读一段就不读全文。

## 步骤

### 1. 定位

`git rev-parse --show-toplevel` 得项目根，再判断走哪条路：

- 用户点名只要**一张图**（「加一张退款流程图」「只更新 20-flow-board」）→ **单图**：读 `00-overview.mmd` 和
  那张图（如果已有），只勘察这张图涉及的代码，画完接 4。别的图一律不碰，除非要给新图加一条 `@link` 入口。
- `docs/arch/00-overview.mmd` 没有 `%% @commit` → **首次**，走 2a。是 `none`（arch-design 画的设计图）也走 2a，
  但以现有地图为底稿：已经写出来的 `planned` 节点转正，其余保留，用户的备注不动。
- 有 → **更新**，走 2b。记录的 hash 等于 HEAD、没有 `+dirty` 且现在也不脏 → 地图已是最新，直接到 6。

不管哪条路，都把所有 `%% @note` 读一遍——那是用户留的备注和新需求。

完成标准：确定了走哪条路；更新时拿到了旧 hash（去掉 `+dirty`）。

### 2a. 勘察（首次）

读 README、依赖清单（package.json / pyproject.toml / Cargo.toml / go.mod 等）、`git ls-files` 的目录树、
入口（main、路由注册、CLI 定义、systemd / docker 配置）。
项目大（跟踪文件超过 300 个，或顶层模块超过 5 个）时，按顶层模块派 Explore 子代理并行勘察，
每个回报：职责、对外接口、依赖谁、关键入口的定义行。

完成标准：列得出全部顶层模块及其依赖方向，选好 3–5 条关键流程，每条都有起点的定义行。

### 2b. 勘察（更新）

1. `git diff --stat <旧> -- . ':(exclude)docs/arch'`（对比到工作区，连未提交的一起算），加上 `git status` 里的未跟踪文件。
2. 一眼能判定是非结构的（文档、测试、样式、纯数值）直接归类，不读。
3. 其余看 `git diff <旧> -- <文件>` 的改动块，只在改动块看不出结构影响时才读整个文件。

判断**结构变化**：模块新增 / 删除 / 改名、依赖方向变了、流程多了或少了步骤、入口变了。纯实现细节不算。
旧地图是 `+dirty` 时，当时的未提交改动可能已经画进图里，会在 diff 里再出现一次——以现有地图为准。

然后：删掉所有图里旧的 `:::changed` 和 `classDef changed`（上次的标记作废）；
旧地图里用行号写的 `@src` 改成锚点（check.py 会逐条报出来）；`planned` 节点如果代码已经写出来了，转成正式节点。

完成标准：每个改动文件都归了类——「结构变化，影响哪张图」或「非结构」。

### 3. 画图

按 FORMAT.md 写 / 改 `docs/arch/` 下的文件。更新时只改受影响的图，代码新增或变化的节点加 `:::changed`。
删掉的东西不留在图里，写进 CHANGES.md。备注照 FORMAT.md 的规则跟着节点走。

在 `00-overview.mmd` 末尾写 / 改 `%% @commit`。在 `CHANGES.md` 顶部加一段 `## 日期 · 旧 → 新 hash`
（首次写「首次生成 · 新 hash」，单图写「补图 / 改图：<文件名>」），下面每条一句中文：变了什么、影响哪张图。

### 4. 校验

跑 check.py，修到退出码为 0。

完成标准：退出码 0；列出的每个没标 `@src` 的节点都确实是外部系统或存储。

### 5. 抽查证据

至少挑 3 条边（更新时优先挑 `changed` 的，单图时都从这张图里挑），按你的笔记回到代码里确认那一行确实有这个调用 / 依赖。
有错就改图，回到 4。

完成标准：抽查的边全部找到了对应代码。

### 6. 交付

运行 `mmd-view <项目根>/docs/arch/00-overview.mmd`（单图就直接开那张图；它自己会转到后台）。然后用中文汇报：

- 首次：有哪几张图、各讲什么，再用 3–6 句话讲清项目的整体结构——这才是用户要的「读懂」；
- 更新 / 单图：只讲变了什么（和 CHANGES.md 同一份），不要重讲整个项目；
- 拿不准、没画进去、做了取舍的地方；
- **疑点**：发现的疑似 bug（读了不存在的字段、接口漏了鉴权等）。图照实画，边标签里注一句，汇报和 CHANGES.md 各列一条，不改代码；
- **备注**：哪些 `@note` 看起来已经被这次的代码实现了——只提醒，删不删由用户决定。

不要 commit。`docs/arch/` 要不要进仓库由用户决定。
